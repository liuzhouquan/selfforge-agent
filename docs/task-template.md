# 任务卡模板

复制到选定 Issue、PR 正文，或 `docs/tasks/任务编号.md`。有现成任务记录时直接补齐，不必重复存放。简单文档改动可压缩为目标、范围、验证和交接四段。

```markdown
# SF-XXXX：具体可观察的行为

- 状态：Ready / In Progress / In Review / Merged / Waiting
- Owner：本任务的人或 agent 标识
- 基线：完整 main SHA；是否已核对远端
- 分支 / 所属 worktree：使用可共享标识，不提交个人绝对路径
- 依赖：无，或明确 PR / SHA / 验收前提
- PR：尚未创建，或链接

## 目标与范围

用户触发什么操作，原来发生什么，本次完成后应观察到什么。

本次不做：明确独立能力或暂未覆盖的环境。
预计触及：公共入口、共享实现、状态/报告、消费者、相关回归。
复用：现有模块/函数；必要新增依赖或抽象的理由。
约束：链接 engineering-invariants 的相关章节和专门契约，避免复制多套数字。

## 验收

| 编号 | Given / When / Then | 证明方式 | 结果 |
| --- | --- | --- | --- |
| A1 | 正常路径的具体输入与输出 | 测试/实际演示的入口和断言 | 未验证 |
| A2 | 本次最重要的错误/边界路径 | 回归或故障注入；缺陷用例应在旧代码失败 | 未验证 |
| A3 | 受影响消费者/兼容状态 | API/CLI/恢复/集成验证，按需要选择 | 未验证 |

## 实施顺序

1. 阅读实际路径，确认复现/契约。
2. 补有区分能力的回归，扩展已有模块。
3. 验证消费者与错误路径，同步实际边界文档。
4. 按 development 验证门槛检查最终组合，再交付。

范围有必要变化时：记录原因、依赖关系和新增验收；独立功能移入后续任务。

## 验证记录

| 命令/演示 | 环境/模式 | 测试树或 SHA | 实际结果 |
| --- | --- | --- | --- |
| 填入完整命令 | 例如 Host、Docker 镜像 ID、CI、真实供应商 | 尚未运行 | 未运行 |

区分 planned command 与已执行结果；写出 passed/failed/skipped 及原因。
外部调用/写入：用了什么授权和范围；mock 或真实；结果与可恢复状态。
公共证据：CI/PR 链接、固定任务/报告哈希；不含原始日志、密钥或隐藏测试。

## Review

- 验收编号是否都有证据；还有哪些明确未完成？
- 错误、取消、部分写入、恢复和输入边界是否与本次变更匹配？
- 序列化/API/UI 等消费者是否真正接收到新行为？
- 是否保留原断言、权限与证据门槛；文档是否只陈述已证明的能力？

## Handoff

- 交付状态：本地实现 / CI 通过 / 已合并，选实际状态
- 当前 HEAD：完整 SHA；未提交内容的归属和用途
- 已完成：对应验收编号
- 未完成/环境限制：具体原因，不用“基本完成”代替
- 最近验证：命令、SHA、真实结果；变更后哪些检查尚未重跑
- 仍在运行：属于本任务的进程/CI 标识及处理方式；没有则写无
- 下一步：一条可直接执行的操作或一个具体待查问题
- 整合/回滚：依赖和保留的工作区/分支；是否已有主分支结果
```

## Handoff

上面的 Handoff 随原任务更新即可。接手者核对实际 Git 状态、开放 PR 和 CI，再信任记录；未提交内容不明确时不能用 reset/clean 消除差异。

“所有测试通过”应展开成具体命令和结果；“环境不支持”应写缺少的 daemon/镜像/依赖以及哪些部分已验证。记录缺失前提后继续可独立推进的授权工作，不把模板当作停止任务的理由。
