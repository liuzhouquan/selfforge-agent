# Coding Agent 协作流程

目标是让一个新 agent 能从仓库文档恢复上下文，交付一个有边界、可验证的改动。任务说明缺少关键参数时先检查仓库和已有记录；常规实现选择自主处理，不把这份流程变成反复确认的审批程序。

## 1. 确认现场

先运行只读检查，记录实际路径、分支和 SHA：

```sh
pwd
git status --short --branch
git rev-parse HEAD
git worktree list
```

按当前授权更新 `origin/main` 并检查开放 PR；离线时明确记录没有核对远端。不要因为 IDE 打开的文件切换到其他项目。

- 发现未提交内容，先辨认哪些属于当前任务；不要暂存、还原或覆盖不属于自己的内容。
- 同时工作的 agent 各用一个独立分支和 checkout/worktree。不要在共享 checkout 中替别人切分支；开始编辑和提交前都检查 HEAD 是否意外变化。
- 现有任务若已由其他分支/PR 承接，先读其差异与交接，避免重复实现。依赖尚未合并时标明依赖 SHA 和整合顺序。
- 保留现有历史；不要通过强推、重建仓库或强制清理持久工作区来省略冲突处理。

需要新工作区时，可在拥有的 checkout 中建立仓库外的 worktree，例如：

```sh
git fetch origin
git worktree add ../selfforge-agent-example -b feat/example origin/main
```

示例路径和分支需换成未占用、由本任务拥有的名称；既有独立 checkout 不必再建一份。

## 2. 写清这一次的任务

按[任务模板](./task-template.md)写简短任务卡。跨模块、状态、权限或外部写操作必须有可检查的任务说明；小型文档修订可直接在 PR 正文写同样的信息。已有 Issue 可承载任务卡，不强制另装任务平台。

任务至少要回答：用户会看到什么行为变化、这次不做什么、复用哪个现有入口、怎样证明完成、哪些错误路径必须覆盖。验收先写行为和观察结果，再选测试命令；“加一个类”“补几个测试”“全都通过”不能单独作为需求。

“继续开发”默认只选择[Backlog](./backlog.md)中的一个 Ready 工作单元。Roadmap 的 Planned/In Progress 表示产品方向，不是本轮全部实现的授权清单。为当前目标必需的共享前提可一起做，但要说明依赖；发现独立的新能力时记入后续任务，避免顺手扩展到另一领域。

复杂任务超过一个独立验收目标时先拆分。拆分依据是行为与回滚边界，不机械规定文件数或代码行数。不要因为一个分支的名字还合适，就持续往里面加入计量、审批、风险分析等独立功能。

## 3. 沿现有执行路径实施

读[模块入口](./development.md#module-entry-points)、[架构](./architecture.md)及涉及模块的[工程约束](./engineering-invariants.md)。先找到 CLI/Web → 公共服务/Runtime → 持久状态/执行器 → API/报告 的实际路径，列出消费者；只改内部对象并不能证明最终 API 保留字段或 UI 能显示结果。

对于行为缺陷，先用临时仓库、故障注入或回归用例复现旧行为，再修复。测试应能区分错误和正确实现；已有断言继续保留。测试替身应遵守真实接口，不能在生产代码加反射分支去兼容过时的 mock。

按本次变更选择相关反例，不必把下表机械地全部执行：

| 变更 | 至少考虑的失败面 |
| --- | --- |
| Git 提交/回退/证据 | 已暂存内容、重命名源与目标、ignored/untracked 输入、symlink、部分失败、写入前失效、重复请求 |
| Runtime/Context/审批 | 一个 assistant 的多项工具回填、坏参数、上下文不足、等待批准期间取消或超时、恢复后的旧状态 |
| Web/序列化 | 路由返回而非仅 manager 对象；缺省/错误字段；localhost/origin 和 workspace guard；UI 使用的实际字段 |
| 用量/费用/风险线索 | 混合供应商/模型、缺失用量或费率、精确模型 ID、同名不同路径、关联与因果的区别 |
| 环境/锁文件 | 错误结构、缺失哈希、版本分叉、输入注入、只读分析与实际安装的界限 |
| Eval | 固定 SHA、参考正/负控、允许修改范围、独立可见/隐藏快照、非空 JUnit、失败分类和无数据泄漏 |

只在任务确实需要时引入抽象、依赖或新服务。复用源码需核对许可证和必要 notices；不修改旁边的教学仓库。

## 4. 用证据结束任务

执行[验证门槛](./development.md#verification-gates)，在任务卡记录命令、环境、实际数量、跳过原因和对应树/提交。mock、离线协议演示、Docker 运行、真实模型调用和真实 GitHub 写操作分别说明；一种结果不能替代另一种。

每个验收编号都要有证据，或明确标为未完成。单元测试绿了不自动证明环境安装、恢复、远端重试或模型能力已完成。失败和超限尝试保留，不修改统计口径凑成功率。修复后再次改源码时重跑相关测试；最终组合由完整回归/CI验证，不相加历史分支计数。

同步文档时把“实现状态”和“实际验证状态”分开。启发式估算不能写成精确 Tokenizer，堆栈关联不能写成因果证明，配置费率估算不能写成实际账单。

## 5. 审查、交付、交接

提交前审查全部 diff、受保护路径和敏感信息。PR 正文以最终行为为准，说明任务/验收、范围、测试和剩余边界；不要沿用过期标题或只列架构名词。若接手他人分支，保留原提交，审查修复另加提交。

按已有用户授权与仓库保护规则推送和合并；文档本身不增加授权，也不要求重复询问。已授权整合时，核对 PR 的 head SHA、基线、审查和 CI 后合并，再确认本地 main、合并树及 main CI；未经验证的结果不能标为已通过。

结束、换 agent 或上下文中断前，填写任务卡的 [Handoff](./task-template.md#handoff)：精确 HEAD、已做/未做、验证证据、仍在运行的命令和一个具体下一步。不要把密钥、原始会话、测试全文、个人路径或课程源码放进公共交接。

接手者先核对 Git/PR/CI 的实际状态，再执行下一步。旧交接中的测试数和“已完成”不代替当前验证；工作区状态不明时先保护现场并完成可独立推进的部分。

## 可直接给下一位 agent 的指令

```text
继续 selfForge Agent。先读 AGENTS.md 和 docs/development.md，核对 Git/开放 PR。
按 docs/backlog.md 选择一个 Ready 工作单元，用 docs/task-template.md 写验收和交接。
读取涉及模块的 engineering-invariants；沿已有 Runtime/Runner 扩展。
只交付当前任务，验证公开入口和关键错误路径，并记录实际测试、跳过和剩余事项。
按本会话已有授权完成提交/PR/整合，不把 Roadmap 中其他功能一起加入。
```
